# ADR-001 — Reliable RabbitMQ order delivery

**Status:** accepted

**Date:** 2026-09-23

## Context

The producer must accept an order through `POST /publish` without making the HTTP caller depend on the consumer being available. RabbitMQ therefore acts as the buffer between the producer and consumer.

The queue must survive a RabbitMQ restart, so the producer and consumer use the same durable queue. Messages published in the default confirmed mode are persistent. During the broker-restart demonstration, messages remained available and were delivered after the consumer caught up.

Publisher confirms are needed because a successful HTTP response should mean that RabbitMQ has confirmed receipt of the message. In confirmed mode, `publishMessage` uses a `ConfirmChannel` and waits for the publish callback before returning. The fire-and-forget demonstration showed the alternative problem: messages published without confirms and without persistence can be lost when RabbitMQ is restarted.

The consumer uses manual acknowledgements because the message should only be acknowledged after its JSON record has been appended to `data/received.jsonl`. Acknowledging before the write could lose a message if the consumer stopped between the acknowledgement and the file write.

The correlation ID must travel through every hop. The HTTP `X-Correlation-Id` is passed to the AMQP message as the `correlationId` property, and the consumer reads that AMQP property and writes it to `received.jsonl`.

## Decision

`connectProducerChannel` creates a RabbitMQ `ConfirmChannel` and declares the queue with `durable: true`. `connectConsumerChannel` declares the same durable queue and uses a small prefetch of 1.

`publishMessage` serializes the payload and, in the default confirmed mode, publishes it with `persistent: true` and waits for the publisher-confirm callback. The demonstration-only `fire-and-forget` mode deliberately uses `persistent: false` and does not wait for confirmation.

`handleMessage` reads `msg.properties.correlationId`, parses the JSON body, appends a JSON Lines record containing `correlationId`, `receivedAt`, and `payload`, and only then calls `channel.ack(msg)`.

The HTTP correlation ID is therefore propagated as an AMQP `correlationId` property rather than relying only on the message body.

## Alternatives considered

One alternative was to acknowledge messages before writing them to `received.jsonl`. This was rejected because a consumer failure after the acknowledgement but before the file write could permanently remove the message from the queue without recording it.

Another alternative was to use the return value of `channel.publish()` as the only indication that publishing was successful. This was rejected because the return value is not the broker's publisher confirmation. The confirmed mode instead waits for the confirm callback.

Using the message body for the correlation ID was also rejected. The AMQP `correlationId` property provides the intended message-level metadata and allows the same identifier to be propagated separately from the business payload.

## Consequences

The design provides durable queue state, persistent default-mode messages, publisher confirmation, controlled consumer delivery, and traceable correlation IDs. Messages can accumulate safely while the consumer is unavailable and can be processed after it restarts.

The trade-off is that confirmed publishing waits for RabbitMQ, so the producer can have higher latency than fire-and-forget publishing. Manual acknowledgements also require the consumer to perform the file write before acknowledging each message, so a slow file system can reduce throughput. With a prefetch of 1, the consumer deliberately processes messages conservatively rather than maximizing parallel throughput.

The queue can still grow if the consumer remains unavailable or slower than the producer, so durability does not remove the need to consider queue growth and storage capacity.
