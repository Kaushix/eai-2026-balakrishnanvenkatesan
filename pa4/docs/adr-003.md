# ADR-003 — Three-source canonical order translation

**Status:** accepted

**Date:** 2026-10-11

## Context

PA4 receives the same logical order from three systems, but each source uses a different representation. The web source is nested JSON and already uses `PROD-001`-style product IDs. The mobile source is flat JSON, uses abbreviated fields such as `oid`, `cust_name`, `pid`, an epoch timestamp, numeric currency codes, and product IDs such as `001`. The B2B source is XML encoded as `windows-1257`, uses attributes such as `sku="SKU-PROD-001"`, and stores quantities as string attributes.

The B2B encoding was particularly important because the order contains Latvian characters such as `Bērziņa` and `Brīvības`. The translator therefore reads the XML as raw bytes and decodes it with `windows-1257` before parsing it with `fast-xml-parser`. The parser also represents XML attributes with the `@_` prefix, and a single `LineItem` can be an object while multiple `LineItem` elements become an array, so the translator normalizes the value to an array before iterating.

None of the sources contains a trustworthy price. Web and mobile contain payment information, while B2B contains payment information including an IBAN. The B2B `UnitListPrice` values are also only legacy list prices and must not be used as the canonical price. The pricing API is therefore the source of truth for unit price, currency, tax rate, and product information.

## Decision

Each source is translated independently into the fixed canonical order model.

`normalizeProductId()` converts source-specific identifiers to the pricing API format: web IDs are unchanged, mobile IDs receive the `PROD-` prefix, and B2B IDs have the `SKU-` prefix removed.

`enrichFromPricing()` calls `GET /pricing/:productId` with the `X-API-Key` header. A successful response supplies the canonical unit price, currency, and tax rate. `toDecimalAmount()` formats the API price with exactly two decimal places, so `4.5` becomes `"4.50"` rather than `"4.5"`.

Pricing failures do not crash the whole translation. A 404 becomes an `UNKNOWN_PRODUCT` warning, while other HTTP or network failures become `PRICING_API_ERROR` warnings. The affected item is dropped and the remaining items continue to be enriched. If every item fails enrichment, the translator returns `order: null`.

Payment information is deliberately filtered by construction rather than copied and removed later. The web `customer.payment`, mobile `pm`/`pan`/`pexp`, and B2B `PaymentDetails` never enter the returned canonical object.

The three translators normalize their timestamps, addresses, statuses, currencies, and product IDs into the same canonical structure. B2B ignores unknown XML elements and the legacy `UnitListPrice`, following a tolerant-reader approach.

## Alternatives considered

One alternative was to store prices as numeric values or integer cents. A decimal string was chosen because the canonical schema requires a string with exactly two fraction digits and this avoids losing the required representation of values such as `4.50`.

Another alternative was to fail the entire order when one product could not be priced. That was rejected because one bad line should not prevent valid lines from being processed; warnings make the partial result explicit.

Caching pricing responses was also considered, but every item currently calls the pricing API so that runtime catalog changes are reflected immediately. This is important because the pricing service, rather than the source fixtures, is the price authority.

## Consequences

The canonical output is consistent regardless of which source produced the order, and sensitive payment data does not cross the translation boundary. Pricing changes are picked up without changing the source fixtures, and individual pricing failures are visible through structured warnings instead of taking down the whole order.

The main cost is that the translator depends on the pricing API being available and performs a request for each line item. There is also deliberate source-specific mapping logic: a fourth source with a new product-ID format, timestamp format, or status representation would require another translation branch.

If the canonical schema gains a new required field, all three translators will need to be updated because the canonical model is not owned by these source systems. Similarly, an unrecognized product-ID format may require an explicit normalization rule rather than being safely inferred. The current design therefore favors clear, testable translation boundaries over a generic transformation framework.
