# ADR-002 — Correlated idle-timeout aggregation

**Status:** accepted

**Date:** 2026-10-03

## Context

The order is split into independent item messages, so the aggregator cannot
rely on the original order message to know which results belong together.
Each item message therefore needs to preserve the order identity and the
original item position.

The aggregator also needs to distinguish a genuinely incomplete order from
one that is simply taking longer because another worker is still processing
an item. A fixed deadline could incorrectly produce a partial result for a
large order, so the timeout needs to measure inactivity instead.

Finally, RabbitMQ can redeliver a result. Counting every delivery would make
the received-item count incorrect and could cause an order to complete early.

## Decision

The router preserves `orderId` and `correlationId` on every split item
message, together with a zero-based `itemIndex` and `totalItems`. The
aggregator groups results by `orderId`. For each order, `in_flight` stores the
correlation ID, expected item count, results keyed by `itemIndex`, and a
`lastActivity` timestamp.

The aggregator uses a 5-second idle timeout, configured by
`AGGREGATOR_IDLE_TIMEOUT_SECONDS` and defaulting to 5 seconds. Every result
received for an order resets `lastActivity`, so the timeout is based on
inactivity rather than a fixed deadline from the order's start. This means a
large order can continue receiving items without being cut off simply
because it has more items.

When all distinct item indexes have been received, the aggregator publishes
one `complete` message containing all collected result messages and an empty
`missingItemIndexes` list. If the order remains idle for the timeout, it
publishes one `partial` message containing the results received so far and
the exact item indexes that are missing.

Results are stored in a dictionary keyed by `itemIndex`. If the same
`itemIndex` is delivered again, the existing result is not added a second
time. A `completed_orders` set also records orders that have already
published their final completion message, preventing a late duplicate from
creating another completion.

For an unknown item type, the router logs the unsupported type and skips
routing that item rather than treating it as one of the known types. This
avoids sending an unsupported item to the wrong worker; the trade-off is
that the item will not produce a worker result.

## Consequences

Correlation survives the splitter because every item retains the same
`orderId` and `correlationId`. If a worker stripped or renamed either field,
the aggregator could no longer reliably associate the result with the
correct order.

The idle timeout makes partial results useful while allowing slow orders to
continue as long as results keep arriving. The trade-off is that an order
with no new result for five seconds is considered stalled, even if a worker
might eventually respond.

Partial results explicitly identify missing `itemIndex` values. Consumers
of `orders.complete` can therefore determine which items still need
attention instead of receiving only a generic incomplete status.

The per-order dictionary and `threading.Lock` keep concurrent orders
isolated and make duplicate handling deterministic. The additional
`completed_orders` set prevents an order from producing more than one final
completion message, including after a late duplicate or late result.

## Alternatives considered

A fixed deadline from the start of an order was rejected because it could
produce false partial results for large orders with many items. Counting
messages without using `itemIndex` was rejected because RabbitMQ
redeliveries could be counted twice. A single global result list was also
rejected because results from concurrent orders could be mixed together.
