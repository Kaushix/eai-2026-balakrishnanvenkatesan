# ADR-004 — Reliable messaging decisions

**Status:** accepted

**Date:** 2026-10-26

## Context

PA5 uses RabbitMQ fan-out messaging to send the canonical order to payment, inventory, and notification consumers. The order body must remain unchanged, so the correlation ID needs to travel separately from the order data. The retry topology also needs to distinguish a first delivery from retry attempts and eventually move failed messages to the dead-letter queue.

Notification processing has an additional problem: the same message can be delivered more than once. A notification that has already been written to the log must not be written again after a duplicate delivery or after the service restarts.

## Decision

The order service generates a UUID v4 with `crypto.randomUUID()` and stores it only in the AMQP custom header `properties.headers.correlationId`. It is not added to the canonical order body and is not stored in AMQP's native `properties.correlationId`. The same header is copied to payment, inventory, and notification result messages so the correlation ID can be traced through the workflow without changing the canonical order schema.

Payment, inventory, and notification use the provided retry/DLQ pattern with `MAX_RETRIES` defaulting to 3. A failed message is negatively acknowledged without requeue, allowing the provided retry topology to send it through the retry queue. After the third failed attempt, the consumer publishes the original message to its DLQ and acknowledges the original message. This keeps retries bounded instead of allowing an indefinitely failing message to remain in the normal queue.

Notification idempotency is persisted in `/data/processed-ids.json`. A correlation ID is considered processed after the notification has been written to `/data/notification.log` and its ID has been persisted. Duplicate messages whose correlation ID is already in the processed list are acknowledged and skipped.

## Alternatives considered

Using AMQP's native `properties.correlationId` was rejected because the assignment requires the correlation ID in the custom `headers.correlationId` field. Using a header also keeps the canonical order body unchanged while allowing the existing retry/DLQ flow to carry the value.

An in-memory `Set` of processed IDs was rejected for notification idempotency. It would prevent duplicates only while the current process is running. After a container restart, the set would be empty and an already-processed order could be logged again. Persisting the IDs in `/data/processed-ids.json` allows the service to restore its processed state after restart.

Using unlimited `requeue=true` was also rejected. A permanently failing message could repeatedly return to the normal queue without reaching a DLQ. The bounded three-attempt retry path provides a clear failure limit and keeps permanently bad messages available for investigation.

## Consequences

The main benefits are traceability without modifying the canonical order schema, bounded failure handling through retries and DLQs, and persistent notification deduplication across service restarts.

The three-attempt limit is intentionally bounded. A legitimately slow or temporarily unavailable downstream that remains unhealthy beyond the retry window can still end up in the DLQ rather than being retried forever. Recovery from that condition therefore requires handling the DLQ.

The persistent idempotency file adds file I/O and rewrites the JSON list when a new notification is processed. It is also designed for the single notification-service instance used by this assignment; multiple replicas concurrently updating the same file would require stronger shared-storage or locking semantics.

If a future consumer forwards a message without carrying `headers.correlationId`, correlation tracing would be lost for that message. Therefore consumers must preserve the header when publishing downstream events.
