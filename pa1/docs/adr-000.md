# ADR-000 — Legacy file ingestion strategy

**Status:** accepted
**Date:** 2026-09-14

## Context

The order export is a legacy fixed-width text file encoded in CP1257 (`windows-1257`). Each valid record is exactly 77 characters long, with fields at fixed column positions. Customer names can contain spaces and Latvian diacritics, so the file cannot safely be parsed by splitting on whitespace.

The customer master is a separate semicolon-separated UTF-8 file. The two files therefore use different encodings and different layouts.

The order file can also contain malformed records. In this dataset, one record is truncated. The ingestion process must not stop because of that record: it must report the rejected line and continue processing the remaining valid orders.

Money values are represented with a comma decimal separator and may contain trailing zeros or negative values. They therefore need to remain decimal strings rather than being converted to JavaScript numbers. Dates are represented as DD.MM.YYYY and have no timezone component.

## Decision

The ingestion implementation uses only Node.js standard library functionality.

The order file is read as raw bytes and decoded explicitly using `TextDecoder("windows-1257")`. Each line is validated against the required 77-character length before its fields are extracted. Valid fields are obtained by slicing the specified fixed-width columns and trimming their trailing padding.

Dates are converted directly from DD.MM.YYYY to YYYY-MM-DD using string operations rather than JavaScript `Date`. Amounts are handled as strings, replacing the comma decimal separator with a period without converting the value to a floating-point number.

Malformed lines are not silently discarded and do not abort the ingestion. They are added to `rejected` with their line number, raw contents, and a reason.

The customer master is decoded as UTF-8, its header is skipped, and customer IDs are stored in a `Map`. After processing the accepted orders, customer IDs that never appeared on an accepted order are returned in `unmatchedCustomers`.

## Alternatives considered

**Decode the order file as UTF-8.**
Rejected because the source file is CP1257. UTF-8 decoding produces incorrect Latvian characters and can introduce replacement characters.

**Split order records on whitespace.**
Rejected because customer names contain spaces. Fixed-width column positions preserve the actual field boundaries.

**Use `parseFloat` for amounts.**
Rejected because floating-point conversion would remove meaningful formatting such as trailing zeros (`45.20` becomes `45.2`) and would change the required representation.

**Use JavaScript `Date` for order dates.**
Rejected because the source value is a plain calendar date with no time or timezone. Direct string conversion avoids ambiguous parsing and timezone effects.

**Throw or silently skip malformed records.**
Rejected because both approaches hide data quality problems. The malformed record must remain visible in the report while allowing the rest of the batch to complete.

**Add parsing or encoding dependencies.**
Rejected because the assignment requires no runtime dependencies and the required functionality is available in the Node.js standard library.

## Consequences

The implementation correctly handles the legacy file contract while keeping the runtime dependency-free. Encoding, fixed-width parsing, monetary representation, date conversion, malformed records, and customer matching are handled explicitly rather than relying on implicit JavaScript conversions.

The main trade-off is that the implementation depends on the documented legacy format: changes to the column layout, encoding, or customer-file structure would require corresponding parser changes. The rejected-record report also makes data-quality problems visible instead of allowing them to become silent data loss.

For a production integration running for several years, the same approach should be extended with stronger schema and format validation, operational logging and monitoring, and an explicit strategy for detecting changes to the upstream export format.
