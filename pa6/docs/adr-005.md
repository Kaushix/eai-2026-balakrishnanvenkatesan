# ADR-005 — Contract-driven checkout saga with explicit compensation

**Status:** accepted

**Date:** 2026-11-02

## Context

The checkout API coordinates four downstream services: payment, inventory, shipping and notification. The required forward order is strict: payment authorization must succeed before inventory reservation, inventory before shipping creation, and shipping before notification delivery. A later failure therefore cannot simply be handled as an isolated HTTP error because earlier operations may already have created external state.

The most difficult boundary is compensation. Payment exposes a refund operation and inventory exposes a release operation, but shipping and notification do not expose compensating endpoints. Consequently, the orchestrator can compensate payment and inventory, but it cannot undo a successful shipping creation or notification delivery. The orchestrator therefore stops the forward saga when shipping or notification fails and compensates only the completed steps for which an operation exists.

Failure classification also required an explicit decision. A downstream business response such as HTTP 422 is different from a request timeout. The orchestrator uses the configured REQUEST_TIMEOUT_MS for downstream calls and records a timeout separately from a normal failed response. A timeout is returned as HTTP 504 when compensation succeeds; a business failure is returned as HTTP 422.

Idempotency created another important boundary. The request is persisted as in_progress before the first downstream call. This means a second request using the same key while the first request is running can return HTTP 409 with idempotency_conflict instead of starting another saga. After completion, the stored response is replayed for the same key and payload. Reusing the key with a different payload is rejected with HTTP 409 and idempotency_payload_mismatch.

The OpenAPI contract also forced details that could otherwise remain implicit: the request is bounded to 50 items, trace entries have a defined structure, the response has explicit saga states, and error codes are documented. Spectral validation now reports no errors.

## Decision

The orchestrator implements the checkout as four sequential asynchronous calls. POST /checkout first validates the request and the required Idempotency-Key, calculates a SHA-256 request hash, and persists an in_progress idempotency record. The payment call is made first, followed by inventory, shipping and notification. No two forward steps are executed in parallel.

Each downstream call is made through callDownstream, which applies REQUEST_TIMEOUT_MS and distinguishes timeout errors from ordinary non-2xx responses. Every executed operation is recorded in the trace with step, status, startedAt, finishedAt and durationMs.

When inventory fails after payment succeeded, compensate performs payment_refund. When shipping or notification fails after both payment and inventory succeeded, compensation runs in reverse order: inventory_release followed by payment_refund. Shipping and notification are never given invented compensation operations because their mock services do not provide them.

A successful saga returns HTTP 200 with status completed. A business failure returns HTTP 422. A timeout returns HTTP 504 when compensation succeeds. If a required compensation operation itself fails, the final result is HTTP 422 with code compensation_failed and status failed.

Idempotency records and saga records are persisted under /data/idempotency-store.json and /data/saga-store.json. A completed result is therefore available for replay after a process restart rather than being held only in memory.

## Alternatives considered

The first alternative was to execute downstream operations in parallel where possible. This was rejected because the assignment requires strict payment → inventory → shipping → notification ordering. Parallel execution would also make compensation ordering and trace interpretation less deterministic.

A second alternative was to return an intermediate HTTP status such as 202 while the saga continued asynchronously. This was rejected because the required API returns the final saga result synchronously, including the completed trace and compensation outcome.

Another alternative was to generate request validation directly from the OpenAPI schema. Instead, the implementation keeps explicit validation in validateCheckoutPayload. This makes the runtime checks visible in the orchestrator code and ensures important bounds, such as the maximum of 50 items, are enforced.

Finally, it would have been possible to add compensating endpoints to shipping and notification. That would make rollback more complete, but it would change the supplied mock-service contract rather than solving the orchestration problem within the interfaces provided. The implementation therefore accepts that those two operations cannot be compensated.

## Consequences

The main benefit is predictable orchestration. The four forward calls have one fixed order, compensation has one fixed reverse order, and the trace records the actual sequence. Timeout and business-failure behavior is also explicit, so callers can distinguish a downstream timing problem from a rejected operation.

Persistence makes retries safer and gives idempotency behavior a stable basis. A successful or failed result can be replayed for the same key and payload, while a different payload cannot accidentally reuse the same key. The cost is synchronous file I/O and the need to keep the persisted schemas compatible with the application.

The design also has limitations. Adding a fifth forward step requires changing the orchestration sequence, compensation rules, trace contract and tests rather than registering a new service dynamically. Two different idempotency keys can also refer to the same orderId; the current saga store is keyed by orderId, so such concurrent requests require care if stronger per-order locking is introduced later.

The inability to compensate shipping or notification remains an accepted consistency limitation. If either operation succeeds and a later operation fails, the orchestrator can compensate only payment and inventory. This is preferable to pretending that a rollback exists when the downstream contract provides no such operation.
